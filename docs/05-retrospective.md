# 个人复盘

## 我认为最难的问题

回看这个项目，最难的部分是让“方案完成”成为可以核对的事实。模型可以提出计划、选择档位和解释原因，但预算是否充足、旧费用是否保留、方案是否真正保存，都需要程序和实际记录支撑。

例如，预算为 10 时，标准方案估算为 12，改成复用方案后是 8。但如果前一个步骤已经发生费用，调整方案时不能把这笔支出清零。项目因此使用逐笔账本，并让估算绑定计划、账本和规则版本，发生变化后重新计算。这个例子让我认识到，Agent 的状态设计和业务约束会直接决定结果是否可信。

保存也是同样的问题。“已保存”的文字说明不足以证明完成，需要事务提交和数据库回读。重试则要区分正常重复调用和连续失败：此前测试暴露过把合法的生成前后两次估算误计为重复失败的问题，最终通过分开计数修正。相关定位和代码修复由 AI 助手执行，我把它们作为本项目设计取舍与复盘的依据。

## 我的决策与调整

我确认先做离线业务验证，再接入真实模型，目的是先明确费用、状态和失败处理的规则，再观察模型能否根据工具返回调整动作。Mock 便于复现，但无法证明模型的决策能力，因此后续补充了真实 API 执行记录。

接入时，我提出将本机 CSV 改为 `.env` 配置，并支持通用 OpenAI 兼容接口，让其他使用者也能用自己的密钥和模型验证。检查使用方式时，我又指出单次命令与完整 JSON 不便于持续交流，推动增加了连续对话、需求增量修改、会话恢复和易读摘要。README 前置安装步骤和清理重复结果，也是为了让交付更容易运行和检查。

这些调整让我意识到，评审者能否快速安装、补充需求并看懂结果，同样是核心交付的一部分，应该在开发早期就考虑。

## 学习收获

首先，需要把模型决策和可信业务状态分开。模型提出动作，程序校验依赖、预算和时间，并记录真实返回；不能用提示词约定替代业务规则。

其次，要区分流程验证与模型验证。离线测试可以检查失败保留、防重复和保存语义；真实模型记录才能说明所测情况下是否根据观察调整了下一步。两类证据都应标明范围和执行版本。

最后，模型的自然语言说明也可能出错。持续对话试用中出现过截止月份复述错误，结构化字段却是正确的，因此终端完成摘要改为从程序校验过的结果展示。对这个项目而言，费用、日期和保存状态都应能从记录中复核。

## 时间与完成情况

个人实际投入估算为 **约 3 小时**，主要用于需求与方案决策、接入准备、使用反馈和交付整理；未按阶段精确计时。自动化执行及等待时间没有完整单独统计，因此不以提交时间差或局部运行窗口推算个人工时。

目前核心 CLI、离线流程、真实模型接入、持续对话和验收材料已经具备。保留的自动化报告为 82 项通过，真实路径与版本边界见 [评估](03-evaluation.md)。

## 不足与下一步

当前检索依赖小规模合成资料和关键词，脚本采用严格事实引用，方案只有有限档位。它能验证规划与约束机制，还没有证明真实营销创作质量、翻译效果、视频制作或商业转化。API token 与模拟业务费用分开记录，但未核对实际账单；也未提供生产级并发和崩溃任务续跑。

如果继续投入，我会优先补充更多素材、费用规则和失败扰动，检验方案调整是否随工具结果变化，并增加保留材料中尚未覆盖的真实模型故障和预算无解路径。随后再压缩工具定义与历史状态带来的上下文开销，进行优化前后的实际对比，最后考虑失败任务续跑和更丰富的方案空间。
